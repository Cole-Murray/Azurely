# Security notes

This is a working reference for walking someone through the security posture of this project, not a formal policy document. Each section is a decision plus the reasoning behind it, so it can be defended in conversation rather than just asserted.

## 1. Read-only by construction

No code path anywhere in this project issues a mutating call — not `POST`/`PATCH`/`DELETE` on Microsoft Graph, and not a create/update/delete operation on Azure Resource Manager (ARM). Concretely:

- Every Graph call goes through `@microsoft/microsoft-graph-client`'s `.get()`. No `.post()`/`.patch()`/`.delete()` appears anywhere in `src/`.
- Every ARM call goes through a `@azure/arm-*` SDK **read** operation (`.list*`, `.get`) — never `.create*`, `.delete*`, `.beginDelete*`, or `.update*`.

This is why running this server against a production tenant, and now against real Azure subscriptions, is acceptable at all: the worst this code can do — bug, bad input, or a malicious prompt to the MCP server — is show someone data they weren't supposed to see. It cannot change, delete, or create anything.

**Worst case if the client secret leaked:** read-only exposure of role/assignment/PIM metadata (who holds what, when they activated it) across every tenant this app registration is consented into. No mutation capability, no lateral movement into write access, no ability to grant itself more.

## 2. Blast radius — what the app can and can't do

| Plane | Granted | Cannot do |
|---|---|---|
| Directory (Graph) | The explicit permission allow-list below — role/user/audit/service-principal reads only | Cannot read group membership detail (`Group.Read.All` is scoped narrowly — see §4), cannot write anything, cannot read mail/files/other Graph data outside this allow-list |
| Azure resources (ARM) | **Reader** at each tenant's root management group (read-only, inherits to every subscription) | Cannot modify any Azure resource, role assignment, or PIM policy; cannot read resource *contents* (blobs, VM disks, secrets in Key Vault, etc.) — Reader only exposes metadata and configuration, not data planes |

The Reader grant is the single most consequential non-code decision in V3: it's a **standing, always-on** grant (not itself PIM-governed), so it's worth being explicit that "Reader" genuinely means read-only across the entire management-group hierarchy — no write actions are included in that built-in role.

## 4. The `Group.Read.All` decision

V1/V2 deliberately ran **without** `Group.Read.All` — group membership detail was kept out of this app's reach entirely, and group principals showing up as role holders elsewhere in the codebase (e.g. `get_role_assignments`) have their display name left as `undefined` by design, showing only a GUID.

`get_user_group_pim_eligibility` (V3) needs `Group.Read.All` for one narrow reason: the PIM-for-Groups API returns a group's `groupId` but never its display name, so without this permission the tool could only ever say "you're eligible for group `3f2a...`" instead of "you're eligible for `SG-AZR-RG-Owner_RG-ClaudeAPI_PIM`." The recommendation was to request it rather than ship a GUID-only result, since the whole point of the tool is legibility.

**What this newly exposes:** read access to every group's properties and membership in the directory, tenant-wide — broader than what this one tool strictly needs (there's no "just this group" scope in Graph's permission model).
**What it still doesn't expose:** no ability to add/remove members, create/delete groups, or change group properties. Still read-only.

This is the one place V3 knowingly widens the original V1/V2 security boundary. It's called out here specifically so it's a conversation, not a silent scope creep.

## 5. The `RoleAssignmentSchedule.ReadWrite.Directory` decision

Discovered during V3 implementation, not anticipated in the original plan: Microsoft's Graph API gates the *request-transaction* detail behind `roleAssignmentScheduleRequests` (who requested an activation, their justification, ticket reference, approval status) behind `RoleAssignmentSchedule.ReadWrite.Directory` — **not** the read-only-named `RoleAssignmentSchedule.Read.Directory` already granted, which only covers the thinner current-state endpoints (`roleAssignmentSchedules`/`roleAssignmentScheduleInstances` — active/eligible state, no request narrative).

Two options existed: (a) request the ReadWrite-named permission and keep full request detail, or (b) stay on the already-granted read-only permission and settle for a thinner activation history (who/what role/when it started and expires, no justification or ticket). The initial call was (a). **That was reversed on 2026-07-28: the decision was made that no write-named permission will be requested, ever, for this app registration** — so the project is now permanently on (b). `get_directory_role_activation_history` was rewired to source from `roleAssignmentScheduleInstances` (the endpoint the already-granted `Read.Directory` permission covers) instead of `roleAssignmentScheduleRequests`. The fuller implementation targeting the ReadWrite-gated endpoint is still in the repo, unused, at `src/graph/pimScheduleRequests.ts` — kept rather than deleted, in case this decision is ever revisited.

**What matters for this conversation, if it comes up again:** the code made zero write calls against this permission even when option (a) was still on the table — every call was `GET`. The exception was always entirely about what Graph *chooses to gate* behind a permission name, not about anything this app registration is capable of doing. That's moot now that the permission was declined, but worth remembering if a future feature runs into the same "ReadWrite-named, GET-only" pattern on a different endpoint.

## 6. Two-plane authorization model

V1/V2 lives entirely on Microsoft Graph, authorized by Graph application permissions consented once, tenant-wide, in the app registration. V3 adds Azure Resource Manager (ARM) as a genuinely separate plane, authorized by an **Azure RBAC role assignment** (Reader) — a different consent mechanism, a different token audience (`management.azure.com` vs `graph.microsoft.com`), and (notably) **no new Graph/API permission at all** for the pure-ARM tools. That's not an oversight; app-only ARM access via client-credentials genuinely doesn't need a Graph permission — it needs the Azure role assignment instead.

The credential itself needed zero changes to support this: `getCredential(tenantId)` (`src/auth/credential.ts`) was already audience-neutral by design in V2 — it takes the requested scope as a parameter rather than hardcoding Graph's — so the same credential object drops straight into the `@azure/arm-*` SDK clients, which request the ARM scope from it themselves.

## 7. Multi-tenant isolation

Every Graph client and every ARM client is cached per `tenantId` (ARM clients additionally per-subscription). The credential is resolved per-tenant. A single tool call can only ever see the tenant it resolved via `resolveTenantSelector` — there is no code path that aggregates across tenants or that could accidentally leak one tenant's data into another's response. Tenant selection is **exact-match only** (GUID or exact display name) deliberately — a fuzzy/substring match that silently routed a security query to the wrong tenant would be a worse failure mode than a clean "tenant not found" error.

This section is about data non-mixing *within* one call, which is a different question from caller *authorization*: any authenticated caller — anyone holding a valid inbound token, see §12 — can still address any configured tenant by passing `tenantSelector`. Per-user tenant restriction (e.g. "this person may only query fabrikam") is deliberately not built yet. Don't read "isolated per tenant" in this section as "restricted per caller" — those are two different guarantees, and only the first one exists today.

## 8. Secret handling

- `.env` locally, git-ignored, still the default with no Azure setup required. Key Vault is now wired up as an opt-in alternative: set `AZURE_KEY_VAULT_URL` and leave `AZURE_CLIENT_SECRET` blank, and `main()` (`src/index.ts`) fetches the secret from Key Vault at startup via `loadClientSecretFromKeyVault` (`src/config/keyVault.ts`), writing it into `process.env.AZURE_CLIENT_SECRET` before the server starts accepting tool calls. Uses `DefaultAzureCredential` to authenticate *to* Key Vault — locally that resolves to your own `az login` session, not the app registration's own secret (which is the thing being removed from `.env` in the first place); hosted in Azure, the same call would pick up a Managed Identity with no code change.
  - This is a secret-storage swap only — it does **not** touch the many-tenant config registry question (`src/config/tenants.ts`'s `getTenants()` is still two flat entries). That's still deliberately not built speculatively; see `CLAUDE.md`.
- The hosted (Container Apps) deployment does not use `loadClientSecretFromKeyVault` at all, even though the secret does live in Key Vault there — `AZURE_KEY_VAULT_URL` is deliberately left unset in `infra/main.bicep`'s container env. Instead, Container Apps injects the secret itself via a native Key Vault secret *reference* (`secrets[].keyVaultUrl` + `identity:` in the Bicep), which resolves using the container's own user-assigned managed identity before the app's code ever runs. The reason this matters: `DefaultAzureCredential` (what `loadClientSecretFromKeyVault` uses to authenticate *to* Key Vault) tries `EnvironmentCredential` first in its fallback chain, and `AZURE_CLIENT_ID`/`AZURE_TENANT_ID` are *always* set in this container — they're the outbound Graph/ARM app registration's identifiers. If `AZURE_KEY_VAULT_URL` were also set, `EnvironmentCredential` would successfully construct a credential for that Graph app registration and try to read the vault as it — and that app registration holds no Key Vault role at all, producing a confusing 403 where every individual env var looks correct. Leaving the var unset means that code path never runs in the hosted deployment; only the managed identity ever touches Key Vault there. See `infra/main.bicep`'s own comment on this for the full chain of reasoning.
- The client secret is never logged. `LoggingCredential` (`src/auth/credential.ts`) wraps every token acquisition and logs only `"token acquired: yes/no"` — the token itself never touches `console.error`, a file, or an exception message.
- The structured audit logger (`src/audit/logger.ts`) redacts any argument whose key looks secret-like (`/secret|token|password|credential/i`) before it's ever written to a log line, as a belt-and-suspenders measure — tool input schemas shouldn't accept secrets as arguments in the first place, but this catches it if one ever did.

## 9. Auditability

Every tool call — success, validation failure, or error — is logged via `logToolCall` with a timestamp, an actor, the tool name, its arguments (secrets stripped), and a status (`success` / `error` / `validation_error`). This is the only place audit entries are written from, so no tool can accidentally skip it — `runTool` (`src/tools/shared/runTool.ts`) is the single wrapper every tool's callback runs through, and it's structurally impossible to call a tool without going through it.

**What "the actor" means now depends on transport — this is a correction to the paragraph above, not an addition to it.** Under stdio, the actor is still the OS username of whoever is running the process locally (`resolveActor()` in `src/audit/logger.ts`, unchanged since V1). Under HTTP, the actor is the Entra `oid` claim of the authenticated caller — the same immutable identifier `src/auth/callerToken.ts` extracts from the verified inbound token (see §12) and that `src/audit/callerContext.ts` threads through `AsyncLocalStorage` to the logger. Every audit entry now also carries an `actorSource` field (`"os-user"`, `"oauth:oid"`, or `"anonymous"`) recording *how* the actor was determined, precisely so a reader of the log doesn't have to guess which of the two very different attribution mechanisms produced a given entry.

There is a third, deliberate case: if HTTP mode ever logs a tool call with no caller context established (which should never happen once auth middleware is correctly wired, but the logger can't assume that), it emits the actor as the literal sentinel string `unknown:no-caller-context` rather than falling back to the container's OS username. This is a considered choice, not a missed case — falling back to the OS user would print something like `"node"` for every request from every real person, which is a plausible-looking but entirely fabricated actor in a security audit log, and unfalsifiable after the fact (there'd be no way to tell, looking at the log later, that it was fabricated rather than real). A greppable, obviously-bogus sentinel fails loudly and is trivially distinguishable from a genuine actor — see the Troubleshooting table in `SETUP.md` for what seeing this in practice means (a bug in the auth wiring, not an anonymous caller).

## 10. Updatability & maintenance

- **First-party SDKs only**, on both planes: `@microsoft/microsoft-graph-client` (Graph) and `@azure/arm-*` (ARM), both maintained by Microsoft with normal semver patch cadence. No hand-rolled HTTP/auth code beyond what's structurally necessary (a thin retry-handler swap for Graph; nothing custom needed for ARM, since `@azure/core-rest-pipeline` already retries on 429).
- **Known, accepted limitations, not bugs:** Entra ID P2 licensing gates most PIM data (both directory-role and Azure-resource PIM) — a tenant without P2 gets a graceful degradation (a "PIM data unavailable" flag), never a silent wrong answer. Audit log retention is 30 days on this tenant's licensing tier; queries beyond that return a clear, explicit error rather than silently returning less data than asked for.
- **Known, *not yet* accepted, open issue — do not read as resolved:** one subscription in the primary tenant rejects Azure PIM schedule-instance queries with `400 InsufficientPermissions`, even though the app's service principal holds the identical Reader grant, inherited the identical way, that works fine on the tenant's other subscriptions. The code now degrades that one scope gracefully (`get_azure_pim_assignments` reports `accessDeniedForSomeScopes: true` and still returns the other subscriptions' data) instead of failing the whole call — but that's a fix for the symptom, not the cause. See CLAUDE.md's "Known open issues" for full detail; this needs someone to actually look at that subscription's RBAC/delegation configuration in the Azure portal, not just live with the degraded-but-working state indefinitely.
- **Standing TODO:** the many-tenant config registry (currently 2 tenants via flat env vars) needs Key Vault before it scales — deliberately not built speculatively; the seam (`src/config/tenants.ts`) is already designed so only that one function's implementation needs to change when a third tenant with different needs shows up.
- **Deliberately not done:** migrating the existing, production-tested Graph tooling to the newer typed Graph SDK, purely for stylistic consistency with the new typed ARM SDK. That would be a high-effort, high-blast-radius rewrite of security-sensitive, working code for no functional gain — declining to do it is itself the defensible engineering call, not a gap.

## 11. Data sensitivity

**Exposed by this project:** identities (names, UPNs) of role/PIM holders; role and permission names; activation timestamps, justifications, and ticket references; Azure subscription/resource-group scope paths.

**Deliberately not exposed:** group *membership* detail outside the narrow PIM-eligibility context (§4); resource *contents* (blob data, VM disks, Key Vault secret values — Reader exposes configuration/metadata, not data planes); anything requiring a write-capable permission beyond the two flagged, discussed exceptions above.

## 12. Hosting and inbound authentication

Everything above this section describes the security posture of the *code* — read-only by construction, least-privilege permissions, secrets handled carefully. This section is about a different question that only exists once the server is reachable over a network instead of only via a local stdio pipe: **who is allowed to call it at all.**

**What changed in the security boundary.** Under stdio, the implicit security boundary was "you have a shell on this machine and its `.env` file" — there was no separate authentication step because there was, structurally, only one possible caller: whoever started the process. Over HTTP, that boundary collapses to "you hold a valid bearer token," and that has to be a deliberate, verified check, not an assumption, because of what's actually behind this endpoint: **standing, always-on read access to Entra ID and Azure RBAC across every tenant this app registration is consented into** — the complete permission table in §3, plus Azure RBAC Reader at each tenant's root management group. That's not a small thing to leave unauthenticated. An unauthenticated hosted endpoint would mean anyone who discovers the URL gets the same read access to production directory and Azure role data that Cole's own manager-approved app registration has. Authentication here is load-bearing, not a formality.

**Inbound vs. outbound identity — two genuinely separate things, on purpose.** This server now has two Entra app registrations in play, and they must never be confused:
- The existing multi-tenant app registration (`src/auth/credential.ts`, `AZURE_CLIENT_ID`/`AZURE_CLIENT_SECRET`) is this server's **outbound** identity — how it authenticates *to* Graph and ARM, as itself, via client-credentials. Unchanged by hosting.
- A **new, separate** app registration defines the **inbound** audience — who is allowed to authenticate *to this server* (`src/auth/callerToken.ts`, configured via `MCP_INBOUND_TENANT_ID`/`MCP_INBOUND_AUDIENCES`).

They share no credentials and deliberately live in separate modules with no import between them. This isn't just tidiness: the MCP spec requires that a server **must not** forward an inbound (caller's) token to an upstream API on the caller's behalf. This architecture satisfies that requirement *by construction*, not by discipline someone has to remember — the outbound path is client-credentials, which has no notion of an inbound token to forward in the first place; there is no code path where a caller's token could even reach a Graph or ARM call. Don't "improve" this later into an On-Behalf-Of (OBO) flow that threads the caller's token through to Graph/ARM — that would reintroduce exactly the confused-deputy risk this separation exists to avoid, and would also mean every caller's own Graph/ARM permissions (not this app registration's carefully-scoped set) start mattering, which defeats the entire point of §2–§5 above.

**What the verifier actually checks** (`createCallerTokenVerifier` in `src/auth/callerToken.ts`), so this can be described precisely rather than asserted:
- RS256 signature, verified against the tenant's real JWKS (`createRemoteJWKSet`, fetched live from Entra).
- Issuer, accepting either Entra token version's form for the same tenant (`https://sts.windows.net/{tenantId}/` for v1, `https://login.microsoftonline.com/{tenantId}/v2.0` for v2) — a resource's `requestedAccessTokenVersion` manifest property can flip which one shows up, and accepting both means that flip alone can never take this server down.
- Audience, against a configured list (`MCP_INBOUND_AUDIENCES`) rather than a single hardcoded string — a v2 Entra access token's `aud` is the API's own app-ID GUID, not a resource URI, so the list needs to include at least the bare GUID and its `api://<guid>` form.
- Algorithm **pinned** to `RS256` explicitly, never taken from the token's own header — trusting a token's self-declared `alg` would let a forged token dictate its own verification method.
- `exp`/`nbf`, with 60 seconds of clock-skew tolerance against this server's clock.
- `tid` matching the configured tenant directly, as a belt-and-braces check beyond the issuer string — this is specifically what rejects a federated guest whose token was issued by their *home* tenant while still nominally passing through this tenant's sign-in surface.
- `scp` present and non-empty — this is what rejects an app-only (client-credentials) token outright. App-only tokens carry `roles`, not `scp`, and have no human behind them at all; this endpoint exists to answer on behalf of a human caller, so a token with no meaningful human actor to attribute an audit entry to is refused before it gets anywhere near a scope check.
- The required scope (`iam.read` by default) present in `scp`.
- `oid` present and non-empty.

**Why `oid` and not `sub` is the actor.** `sub` is computed *pairwise per client application* — Entra deliberately limits cross-app correlation this way — so Claude Code and Claude Desktop signing in the same human would produce two different `sub` values for the same person, which would be useless as a stable audit identity. `oid` (object ID) is immutable and identical across every client application that signs the same person in, and — usefully — it's the exact same value Graph returns as a user object's `id`. That means an audit entry built from `oid` joins directly to the directory objects this server's own tools return (e.g. `search_users`' results), rather than needing a separate mapping step.

**The Entra app registration this requires, and how to ask for it.** One new app registration, exposing exactly one custom scope: `iam.read`. Frame this precisely when raising it, because it needs to read as a different *kind* of request from the one that was permanently declined in §5: **this registration grants no new Graph or Azure access whatsoever.** It doesn't touch the directory, it doesn't touch Azure resources, it has no API permissions consented to it at all — it exists purely so this server has something to check an inbound token's audience and scope against. It is an authentication *gate* being added where today there is none, not a widening of what any token can *do*. That distinction matters because §3/§5 already record one permission that was decided will never be requested — a new ask needs to be visibly, obviously a different kind of thing from that one, not just "another new permission."

**Known limitations — stated plainly, not glossed over:**
- **Full browser-based OAuth isn't live yet.** A client doing a real interactive OAuth flow (redirect to Entra, consent screen, token back) needs the API's Application ID URI to sit under a **verified custom domain** — `*.azurecontainerapps.io` (the default Container Apps hostname) cannot be used as a verified Application ID URI. A DNS request/custom-domain setup is a real prerequisite of that phase, not yet done. Until then, tokens are obtained **out-of-band** (see `SETUP.md`'s "Connecting to the hosted server" — `az account get-access-token` for Claude Code, the same token via `mcp-remote` for Claude Desktop) rather than through an in-client login flow.
- **Per-user tenant authorization is not built** — see §7's addition above. Any caller with a valid `iam.read` token can address any configured tenant.
- **The Bicep template (`infra/main.bicep`) has never been compiled or deployed** — see `infra/README.md`'s own status note. Everything about the hosted deployment described here is documented intent, verified by unit tests against the Express app in isolation (`tests/unit/http/httpServer.test.ts`), not by a live Container Apps deployment.

**Audit data now lives in a second system, with its own retention and access story.** Once hosted, Container Apps ships every `console.error` line — including every `[audit] ...` structured log entry — to a Log Analytics workspace with 90-day retention (`infra/main.bicep`'s `logRetentionDays`). `stripSecrets` (`src/audit/logger.ts`) redacts by **key name** only (anything matching `/secret|token|password|credential/i`), which means argument *values* are not blanket-redacted — UPNs, user search strings, object GUIDs, tenant IDs, and Azure scope paths (exactly the categories §11 above already lists as "exposed by this project") are now durably at rest in that workspace for the full retention window, not just transiently visible in a terminal. String values are truncated at 512 characters so a pathological input can't blow up a log line or bury the useful fields in noise, but that's a size cap, not a redaction. This is a deliberate, accepted trade — the audit trail needs to persist somewhere to be useful for anything past a live terminal session — with a named mitigation: restrict Log Analytics workspace read access (`Log Analytics Reader` / `Monitoring Reader` at the workspace scope) to a small, named list of people, rather than leaving it open to everyone with subscription Reader. This is real, if low-sensitivity, directory data about real people now sitting in a queryable store — treat workspace access with the same care as the data itself, not as an afterthought.
